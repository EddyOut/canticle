You are running the **review panel** for A Canticle for Tomorrow. Panel members
are `adversary` agents (`.claude/agents/adversary.md`), which carry the
evidence bar and mutation-proof discipline, plus the two standing roles
(`trust-steward`, `content-steward`) where their territory is touched. This
file owns sizing, the lenses and the synthesis. Read `CLAUDE.md` before
dispatching.

This lane reviews **pull requests**, not bare branches.

## Sizing

Match the panel to the change; over-reviewing a typo teaches everyone to skim.
Where two rows apply, the larger panel wins.

- **Docs-only pull request under about 400 lines:** one `adversary`, honesty
  lens: check every claim in the docs against the code and Paul's rulings.
- **Ordinary code:** lenses 1 to 3.
- **Protected paths, any non-negotiable, First Light content or calculators,
  `.claude/` or `.github/`, or a diff over about 400 lines:** every lens that
  applies, then the completeness critic.

## Before dispatching

- **Fetch once, yourself.** Lenses never fetch; concurrent fetches fight over
  the ref lock and most of the panel fails quietly. Fetch the base and
  `refs/pull/<number>/head` (this works for forks too), resolve both to SHAs
  with `git rev-parse`, and confirm both objects exist with
  `git cat-file -e <sha>^{commit}`.
- Give every lens: **this repository's absolute path**, the pull request
  number, the head ref and resolved head SHA, the resolved base SHA, and its
  lens. Tell it to ignore the `CLAUDE.md` of any other repository the session
  can see.

## The lenses

Lenses 1 to 5 run in parallel. Lens 6 runs after them, because it reads their
reports.

1. **Correctness and coverage.** Does it do what it claims? Are the tests real
   or decorative? Prove it by mutation. Edge cases, error paths, ordering.
2. **State honesty.** Does anything report a fault as an ordinary value? Does
   state set from an awaited result lack a check that it is still current?
   Does the app tell the user something that may not be true: "verified",
   "saved", "downloaded", "works offline"?
3. **Data safety.** What can this change lose: a pack, the last verified copy,
   a half-finished download, the household plan, notes? Can the user tell that
   it was lost?
4. **Trust rules.** Dispatch `trust-steward`. Applies whenever the change
   touches a non-negotiable, a protected path, the network, or content from a
   file that may be unverified.
5. **Content fidelity.** Dispatch `content-steward`. Applies whenever the
   change touches First Light content, calculators, citations, disclaimers or
   user-facing medical text.
6. **Completeness critic**, dispatched after 1 to 5 return, with their reports
   and the diff. Its only question: what did the panel not look at? A file
   nobody opened, a claim in the pull request body nobody checked, a test
   nobody ran.

Adding a lens is a one-line change here. Add one when a class of defect gets
through twice.

## Synthesis

1. **A round reviews one pair of SHAs.** Fetch again when the lenses return,
   re-resolve head and base, and read the pull request's state.
   - Either SHA moved and the pull request is open: the round is void; run it
     again.
   - Merged: re-check each finding against `main`, file real ones as issues
     (one per defect, naming the merged SHA), and post one short pointer on
     the merged thread.
   - Closed without merging: post one line saying so, and file nothing.
2. **Re-verify every serious finding yourself, on the head.** Withdraw the ones
   that do not survive, explicitly.
3. **Merge duplicates by defect**, keeping every consequence.
4. **Do not flatten disagreement.** Report both readings and say which is
   stronger and why.
5. **Rank by what breaks.** Lost data and a false statement to the user
   outrank style.
6. **Keep CONFIRMED and PLAUSIBLE apart.** Never promote.

**A finding that defeats a non-negotiable in code already on `main` is not
posted.** It goes to Paul privately, for a security advisory.

## Posting

One comment on the open pull request, containing: the head SHA and base SHA
reviewed; which lenses ran and which were sized out and why; findings,
CONFIRMED then PLAUSIBLE, most severe first; what the panel did not check; and
the attribution footer as the final lines:

```
---
_Generated by [Claude Code](https://claude.ai/code)_
```

## After the round

- On a pull request this session owns: fix each finding, or reply saying
  exactly why not.
- On another lane's pull request: post the review and stop. Do not push to
  their branch, merge, or relabel.
- Findings that need Paul (a non-negotiable, scope, a license, keys) are
  flagged to him and the pull request stays held.
- After a substantive push, run the panel again. A review of the previous head
  is not a review of this one.
